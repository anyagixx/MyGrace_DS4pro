## 1. TL;DR — вердикт в одном экране

**Что это:** сильная, осмысленная идея (context engineering для агентов: «сначала индекс — потом детали») с аккуратно написанным для своего размера CLI, но **стадия — рабочий прототип, а не продукт v1.0.x**.

**Главный разрыв:** проект обещает дисциплину, которую сам не соблюдает и не проверяет:
- репозиторий **не догфудит собственную методологию** — в нём нет `docs/`, `mygrace lint --path .` падает (exit 1), только 2 из 15 файлов `src/` содержат хоть какое-то подобие контракта;
- линтер — «флагманский контроль качества» — **не проверяет почти ничего из того, что заявлено** (проверено: изменение PATH в модуле, дубли записей, битый XML, превышение лимита индекса, отсутствие контракта — всё проходит с «0 ошибок»);
- **опубликовать пакет в текущем виде нельзя**: тарбол npm не запускается (`Cannot find module './grace-doctor'`), а сами пакеты `@osovv/*` вообще отсутствуют в npm (404);
- **MCP-слой** (главная фича для DSH) регистрирует 15 инструментов, но **любой вызов падает**, если бинарник `mygrace` не в `PATH` — а ни один путь установки этого не обеспечивает;
- **безопасность**: XML-файлы репозитория управляют выполняемой командой → при `mygrace test` возможен запуск произвольного кода (воспроизведено); id модуля позволяет читать файлы вне проекта (воспроизведено);
- **метрика «Measured Token Savings» — это строки, а не токены**, и она завышена на ~16–19 п.п. на ключевой строке.

## 3. Что реально работает (сильные стороны — без скидок)

1. **Идея и read-layer работают.** Индекс-first + per-entity файлы действительно режут контекст: на демо-проекте статус читается в 39 строк вместо 363, работа с модулем — 30 вместо 173. Это не «вау-магия», но это правильная инженерия контекста, и она воспроизводима.
2. **`findProjectRoot` починен по-настоящему.** Ограниченный обход вверх (`grace-common.ts:22–31`) корректен, завершается за ~30–55 мс на любом пути, есть регрессионный тест. Это ровно тот случай, когда «в CHANGELOG написано — и это правда».
3. **Код читается.** Единый стиль, разумные имена, `grace-common.ts` реально централизует общее, `grace-mcp-commands.ts` — чистое, тестируемое отображение tool→argv (лучший файл в дереве), `verify` переиспользует `runModuleTests`, а не копирует.
4. **Тесты — не mock-театр.** Все 10 файлов `test/` импортируют настоящий `src/`, сторонних библиотек моков нет; реальные `spawnSync`-запуски, round-trip тесты патча конфига, тесты exit-кодов `verify`.
5. **MCP-сервер технически живой.** Хендшейк проходит, ровно 15 инструментов, описания осмысленные; при наличии бинарника в PATH `list_modules`/`status`/`lint`/`show_file`/`doctor` реально отдают полезные данные (проверено).
6. **`init-dsh` end-to-end работает.** На пустом каталоге создаёт валидный каркас, и `lint` на нём сразу 0/0 — это хороший «первый день» UX.
7. **Инсталлятор в legacy-режиме идемпотентен и аккуратен с формой конфига.** `- insert:`-строка, имя `@deepseek-ai/dsh-mcp-client`, `transport/serverName/command/args` — всё совпало с реальным DSH (сверено с `dsh-app-boot/lib/index.js:61–101`, схемой загрузчика и официальным шаблоном MCP); `--uninstall` восстанавливает `cordis.patch.yml` байт-в-байт; чужие строки профиля не трогает.
8. **Скиллы сделаны правильно по форме.** 15 `SKILL.md` с валидным DSH-frontmatter (`name`/`description`/`whenToUse`), ~10.4k токенов на все, формат — ровно как у `dsh-skill-filesystem`.
9. **Часть периферийных пакетов — настоящая.** `dsh-skill-mygrace` (15 скиллов) и `dsh-mygrace-rtk` (hook `tools/execute`, реальная перезапись команд) работают; это не заглушки.
10. **Честные куски документации есть.** README-таблица MCP-инструментов (15/15 имён), версия, матрица платформ с пометкой «metadata stubs» — точны.

**Вывод по сильным сторонам:** это не «пустышка на вибрациях». Автор понимает, что делает, и умеет писать аккуратно. Проблема — не в квалификации, а в **дисциплине доведения и в проверке собственных утверждений**.

## 4. Что сломано: находки по severity

### 4.1 CRITICAL (блокеры релиза; всё воспроизведено)

**C-1. Опубликованный пакет не запускается.** `package.json:31–47` перечисляет 10 файлов `src/`, а `src/grace.ts:26–30` импортирует 11 локальных модулей; в тарболе нет `grace-context`, `grace-doctor`, `grace-packet`, `grace-test`, `grace-verify`. Проверка: `bun pm pack` → 46 файлов → распаковка → запуск: `error: Cannot find module './grace-doctor'`. `prepublishOnly` это не ловит, потому что проверяет репозиторий, а не собранный артефакт. **Релиз-гейт отсутствует.**
-> `analysis/04-integration-packaging.md` §4, `analysis/01-core-code.md` C-1.

**C-2. Пакеты не опубликованы.** `npm view @osovv/mygrace-cli` → E404; то же для `@osovv/mygrace-dsh`, `@osovv/dsh-skill-mygrace`. Первая же строка Quick Start README (`bun add -g @osovv/mygrace-cli`) невыполнима. Публичный GitHub-след: v0.0.3 (2026-04-10), 0 звёзд.
-> `analysis/03-docs-methodology.md` §2-D.

**C-3. MCP-инструменты мертвы без глобального бинарника.** `src/grace-mcp.ts:22` (`MYGRACE_BIN || "mygrace"`), `:229` (`execFile`). Ни `install-dsh`, ни bundle-хост не задают `MYGRACE_BIN`/абсолютный путь. Итог: 15 инструментов видны, **каждый вызов** → `MyGRACE MCP error: Executable not found in $PATH: "mygrace"` (воспроизведено и мной, и двумя аудиторами). Это главная фича «для DSH» — и она не работает ни в git-checkout, ни через `bunx`.
-> `analysis/04-integration-packaging.md` C3; `analysis/01-core-code.md` §1.2.

**C-4. `install-dsh --bundle` невозможен как заявлено.** В тарбол не входит `packages/mygrace-dsh` (в установленной копии — uncaught ENOENT в `src/grace-install.ts:372`). В checkout `dsh plugin add` записывает только `link:` и **не ставит `file:`-зависимости** бандла: в профиле один симлинк, четыре строки бандла нерезолвимы при загрузке. Host-плагин ещё и не может найти `@deepseek-ai/dsh-mcp-client` (`createRequire` → MODULE_NOT_FOUND). «Verified live» в CHANGELOG проверял только строки `--dump-config`, не загрузку и не MCP.
-> `analysis/04-integration-packaging.md` C2/C4, §3.2.

**C-5. Произвольное выполнение кода из XML репозитория.** `mygrace test`/`verify` берут executable из `<module-checks>` и **добавляют `<file>` как argv** (`src/grace-test.ts:76–78`). Воспроизведено: `<check-1>./run-checks.sh</check-1>` → скрипт репозитория выполнен; аудитор воспроизвёл и `bash -c …` через два `<file>`. Без `--module` команда проходит **по всем модулям** индекса. Т.е. клонирование репозитория + одна команда агента = RCE. Для инструмента, который сам учит агентов запускать эти команды, это провал границы доверия (нет allowlist/подтверждения/`--dry-run`).
-> `analysis/01-core-code.md` H-1.

### 4.2 HIGH (искажают результаты / теряют данные / ломают контракты)

- **H-1. `<module-checks>` читается не оттуда, куда его пишут.** Шаблон `templates/verification/V-M-XXX.xml.template:6–8`, скилл `grace-verification:39` и демо кладут его в **verification-файл**, а `grace-test.ts:31–36,76` читает из **module-файла**. Следствие: во всех проектах «по инструкции» кастомная команда проверки **молча игнорируется**, всегда выполняется `bun test`. (Проверено мной и ещё двумя аудиторами независимо.) Это прямо отменяет Принцип №5 «Verification is architecture».
- **H-2. Линтер не проверяет то, что заявлено.** Экспериментально: (а) изменение `PATH` в модуле при неизменном индексе → 0 ошибок; (б) битый XML в индексе → «passed»; (в) дубли записей → 0; (г) индекс на 216 строк при лимите ≤100 → 0; (д) модуль без контракта/блоков → 0; (е) несуществующий файл в `PATH` → 0. Реально проверяются: наличие/сиротство записей, `verification-ref`, парность блоков, «generic tags», и **STATUS-drift как warning** (не валит exit-код). «The knowledge graph is always current» — это пожелание, а не свойство.
- **H-3. `lint --format json` всегда exit 0.** `grace-lint.ts:283–286` (`return` до `process.exit`). Тот же проект: text → 1, json → 0. Машинный формат, который используют CI и MCP, рапортует успех при ошибках. Аналогично `doctor --format json` и `status` (всегда 0).
- **H-4. Path traversal через id модуля.** `packet ../../../../analysis/outside-secret` прочитал XML **вне проекта** (проверено; в MCP — тоже). `focus`/`test`/`verify` — тот же путь; `install-dsh --profile ../../evil` пишет конфиг вне `$DSH_HOME`.
- **H-5. Regex-«парсер» XML.** `grace-common.ts:34–40,48`: `>` внутри атрибута молча теряет запись; одинарные кавычки → `{}`; `Phase-1a` обрезается до `Phase-1`; нестандартные id (`M_AUTH`) невидимы для проверок (проверено). Валидации well-formedness нет вообще.
- **H-6. Сырые стектрейсы вместо ошибок.** `status`, `module`, `context-cost`, `file` на обычных условиях (нет `docs/`, EACCES, `docs/modules` — файл) печатают стек Bun. Graceful-путь есть только у `lint`.
- **H-7. Инсталлятор правит чужой конфиг строками, без валидации YAML и атомарности.** Бэкап перезаписывается, `id: mcp-mygrace-extra` даёт ложное «already present», битый YAML дописывается молча, read-only файл → EACCES после уже скопированных скиллов. `--uninstall` оставляет `.mygrace-backup`, пустой `skills/`, pnpm-метаданные и печатает инструкцию активации.
- **H-8. Тесты слабее, чем звучит «107 passing».** Mutation score 67%: `lintMarkup`, `lintVerificationRefs`, `lintXmlTags` заменяются на `return []` без падения сюиты — т.е. флагманский детектор можно сломать незаметно. 12 из 107 тестов — тавтологии из демо (`return true` + `expect(...).toBe(true)`). Нет ни одного теста на MCP-runtime, `install-dsh` end-to-end, `init-dsh`, `file show`, битый XML, JSON exit-коды.
- **H-9. «Measured Token Savings» измеряет строки.** `measure-context.ts:22–25` считает строки; в токен-/байт-прокси те же read-set'ы дают ~80/64/54 вместо 89/83/55 (ключевая строка завышена на ~16–19 п.п.). «Savings grow with project size / index stays flat» не измерялось и неверно: на синтетике 12→200 модулей read-set растёт с ~38 до ~477 строк (≈2.3 строки/модуль). В 7 файлах живут ещё и «96–97%» — против собственных 89/83/55.
- **H-10. Демо-проект — фасад.** `examples/demo-store`: 12 байт-идентичных заглушек `return true`, 0 импортов, 0/12 функций с аргументами, сгенерированные тесты-тавтологии; при этом `verify` рапортует «12 ok», включая 5 `pending`-модулей. Как фикстура структуры — нормально; как «dogfooding evidence» — нет.
- **H-11. Дрейф документации.** Счёт скиллов одновременно **15 / 14 / 12** в 10+ файлах (правда — 15); список MCP-инструментов: README 15 ✓, `AGENTS.md` 7, `grace-cli/SKILL.md` 7; корневой `AGENTS.md` — устаревшая копия шаблона; 34 из 59 проверенных утверждений ложны; `lefhook.yml` (опечатка) — хуки не работают; CI нет вообще.
- **H-12. Методология сама себе противоречит.** Лимит индекса ≤100 строк при 1 строке/модуль ⇒ максимум ~92 модуля, а заявлено «20–200+»; контракты размеров (модуль 30–80, фаза 50–200) нарушены и шаблонами (шаблон фазы — 8 строк), и официальным демо (модули 12–13 строк) — и именно на этом нарушении держатся «сэкономленные» проценты; архивирование фазы по 5 документам **ломает lint** («Orphaned index entry»); «status из 3 индексов» — неправда (там полный lint-скан).

### 4.3 MEDIUM / LOW (выборочно, полный список — в приложениях)

- Нет `tsconfig.json`, нет typecheck-скрипта, `typescript` в devDeps декоративен — типы не проверяются никогда (`tsc` даже не стартует).
- Только 2 из 15 файлов `src/` содержат следы `MODULE_CONTRACT` (и то не полноценные) — Принцип №1 не соблюдается в собственной кодовой базе.
- MCP: имена инструментов в DSH имеют префикс `mcp__mygrace__…`, во всех доках — без него; `path` обязателен в схеме, но маппер молча подставляет `"."`; `compact: true` в схеме не применяется; MCP теряет stdout при падении (`Command failed: …`).
- Панель статуса — статическая декоративная карточка без данных; инжектит несуществующий `@deepseek-ai/dsh-client-runtime`; `private: true` блокирует публикацию цепочки.
- Инсталлятор зашивает абсолютные пути и текущий bun в конфиг пользователя (ломается при обновлении/переносе), панель требует голый `pnpm` и молча «скипается» с exit 0.
- `verify --all` объявлен, но не читается; `TOOL_NAMES` — мёртвый код; `module-checks` разбирается `split(" ")` (кавычки не поддерживаются); `formatTable` падает на «рваных» строках; неизвестные флаги молча игнорируются.
- Windows: `spawnSync("pnpm"/"dsh")` не умеет `.cmd`-шимы (статический анализ); `/tmp`-независимая часть не проверялась.

## 7. Что делать: приоритезированный план

### P0 — до любого упоминания «v1.x» / публикации (оценка: 2–4 дня)

2. **Решить судьбу `--bundle`:** либо вырезать его из README/CLI до реализации, либо (а) включить пакеты в тарбол, (б) убрать `file:`/`private:true`, (в) объявить `@deepseek-ai/dsh-mcp-client` зависимостью и резолвить его штатно, (г) прогнать реальный boot на temp `DSH_HOME` с вызовом MCP-инструмента.
3. **Починить MCP:** задавать `MYGRACE_BIN` (или exec `process.execPath run <abs grace.ts>`) в генерируемом конфиге; сделать `path` необязательным с корректным cwd; вернуть stdout на ошибках; убрать 30-секундный лимит для `test`/`verify`.
4. **Закрыть RCE/traversal:** allowlist/opt-in для `<module-checks>`, подтверждение или `--dry-run`, санитайз id (запрет `..`, `/`, `\`, абсолютных путей) во всех командах и MCP; запретить `--profile`/`--dsh-home` с `..`.
5. **Линтер — либо с зубами, либо с честными названиями в доках:** проверять `PATH`↔файл, `DEPENDS`↔импорты, phase-status, лимиты строк индексов/сущностей, well-formedness XML, дубли; warnings должны валить CI (флаг `--strict`); `--format json` → правильные exit-коды.
